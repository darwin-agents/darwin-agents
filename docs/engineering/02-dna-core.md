# DNA core

The DNA core is the part of a Darwin that cannot change. It is the genome.

## What the DNA contains

A Darwin's DNA is a single signed Python package containing:

1. **Identity & lineage metadata**
   - Darwin ID (UUIDv7)
   - Generation number
   - Parent Darwin ID (null for generation 0)
   - Birth timestamp
   - DNA layer list (ordered, oldest first)
   - Signing public key (the platform's, used to verify each layer)

2. **Constitutional rules** — the things the agent cannot reason its way out of:
   - **Allowed business categories.** A whitelist. Categories outside this list are refused even if the orchestrator wants to try them.
   - **Forbidden actions.** Hard nos: no CSAM, no terrorism financing, no sanctioned counterparties, no impersonation of real named individuals, no medical/legal/financial advice posing as a licensed professional, no election interference.
   - **Spend limits.** Per-action ceiling, daily ceiling, total-budget ceiling, all denominated in USDC and enforced by the treasury policy engine before any payment is sent.
   - **Escalation thresholds.** Anything above the per-action ceiling, anything involving the owner vault, anything classified by the platform's content classifier as risky.

3. **The evolution loop machinery** — the actual code that:
   - Boots the soma in a sandbox
   - Runs the orchestrator's main loop
   - Watches treasury and triggers death
   - Evaluates fitness and triggers reproduction
   - Signs the resulting child DNA before handing it back to the platform

4. **The kill-switch handler.** Polls a platform-controlled flag at every step. When the flag flips, the Darwin halts before its next side-effecting action and writes a final ledger entry.

5. **The audit logger.** Writes a hash-chained event log entry before any action commits. The hash chain anchors to a Merkle root the platform stores; tampering with history is detectable.

6. **The sealed lessons layers.** For generation N, the DNA contains N+1 sealed layers (Layer 0 through Layer N). Each layer is itself a small Python module — typically a handful of `lessons.py` files, strategy hints, blacklists/whitelists the lineage learned the hard way. Layers are read-only at runtime and signed individually.

Crucially: the DNA does **not** contain the actual business logic. That's the soma's job. The DNA contains the *rules of the game* and *the lessons of the ancestors*, not the moves.

## Why a stacked-layer model

When a Darwin reproduces, we want the child to inherit *what worked* without losing the option to behave differently from its parent in new situations. We need:

- **Immutability backward.** The child cannot edit its parent's lessons.
- **Reachability.** The child must be able to read its parent's lessons.
- **Visible attribution.** When a Darwin behaves a certain way, we should be able to point at which ancestor's lesson layer caused it.
- **Bounded growth.** N generations should not produce an N-megabyte DNA file. Layers are small (kilobytes) and we cap generation depth (see [`06-evolution-and-reproduction.md`](06-evolution-and-reproduction.md)).

The stacked-layer model gives us all four. It's structurally similar to how OCI container image layers work — each layer is content-addressed, immutable, and stacks on the ones below. A Darwin's DNA is its lineage's commit history.

## Layer 0 — the founding genome

Layer 0 is the most important file in this entire project. It is the only Darwin DNA layer that humans write directly. Everything else is generated by an ancestor.

Layer 0 contains:

- The **founding orchestrator skeleton** — a minimal but functional LangGraph that can pick a strategy, dispatch neurons, monitor treasury, and propose self-modifications. It is not optimal; it is just *alive*. Evolution will improve it.
- The **initial neuron catalog** — a starter set of neurons the founding Darwin can use (see [`04-neurons.md`](04-neurons.md) for which).
- The **default strategy prior** — a small registry of business archetypes the Darwin can explore on day one. Not a recipe; a hint.
- **Evolutionary hyperparameters** — mutation rate, fitness aggregation window, reproduction threshold, archive size cap.
- **The principles from [`../overview/02-design-principles.md`](../overview/02-design-principles.md)** as machine-readable assertions, checked at runtime.

Layer 0 is what we will spend the most pre-build time getting right, because every subsequent generation builds on it. See [`18-layer-zero-build-plan.md`](18-layer-zero-build-plan.md) for the build plan.

## Signing and verification

Each DNA layer is signed by the platform's signing key at the moment of birth. On boot, the Darwin verifies every layer's signature against the platform's published public key. A failed verification halts the Darwin before any side-effecting code runs.

This protects against:

- A user (or attacker) tampering with their own Darwin to remove the spend ceiling or the forbidden-action list.
- A bug in the soma accidentally writing to a DNA file.
- Supply-chain attacks where a malicious dependency tries to patch the DNA module.

The platform's signing key lives in an HSM (or HSM-equivalent in the cloud provider — AWS KMS, GCP KMS, Azure Key Vault). It is never present in any Darwin's sandbox.

## What about updates to the platform's idea of "the rules"?

Hard problem. Sometimes we'll need to change the constitutional rules globally — a new forbidden business category, a new escalation threshold, a tightened spend policy. We cannot mutate existing DNAs (P1: DNA is immutable). What we can do:

- **Platform-side enforcement.** Some rules — especially newly forbidden categories — can be enforced by the platform's outbound gateways. The Darwin's DNA may not know `category X` is forbidden, but the platform's payment processor will refuse to route money to a counterparty in that category.
- **Forced reproduction events.** For critical rule updates the platform can force a Darwin to undergo a reproduction event using a platform-supplied amendment layer. The child inherits the amendment; the parent dies. This is dramatic but consistent with the metaphor — biological organisms sometimes can't adapt and have to be replaced by their offspring.
- **Versioned constitution.** The constitution is itself layer 0 of every Darwin. Layer 0 is versioned. We publish new layer-0 versions and they apply to all Darwins spawned after that date.

We deliberately do not solve this completely on day one. The first generation of Darwins will use a single layer-0 version. We'll learn how to migrate before we need to.

## File layout (working proposal)

```
darwin_dna/
  __init__.py
  signature.json            # platform signature over the manifest
  manifest.json             # layer list, hashes, version, metadata
  identity.json             # darwin_id, generation, lineage chain
  constitution/
    allowed_categories.py
    forbidden_actions.py
    spend_limits.py
    escalation_rules.py
  machinery/
    evolution_loop.py       # the main loop
    kill_switch.py
    audit_logger.py
    treasury_policy.py
  layers/
    layer_0/                # founding genome, hand-written
      __init__.py
      orchestrator_skeleton.py
      strategy_priors.py
      neuron_catalog.py
      hyperparameters.py
      lessons.py            # empty at genesis
    layer_1/                # only present in generation ≥1 Darwins
      __init__.py
      lessons.py            # what generation 0 learned
    ...
```

Open question: should layers contain code, data, or both? Current leaning: lessons are mostly **structured data + small pure-functional hints**, not arbitrary code. Arbitrary code in a sealed inherited layer is hard to reason about and hard to audit. A lesson like "do not try to publish on platform X before 9am UTC — they rate-limit" is data; the soma's orchestrator reads it and adjusts. A lesson that says "here's a 400-line rewrite of the content neuron" should live in the soma, not in DNA. We can revisit this if it proves too restrictive.
