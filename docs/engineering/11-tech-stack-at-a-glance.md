## What we explicitly chose against (and why)

A few decisions worth surfacing because they'll come up:

- **No microservices on day one.** The platform starts as a modest modular monolith (FastAPI app + Next.js app + the supervisor). We split services only when scaling pain forces it. The Darwins themselves are isolated; the _platform_ doesn't need to be.
- **No Kubernetes operator framework for Darwins.** Tempting (`apiVersion: darwin.io/v1; kind: Darwin`). Premature. The supervisor handles lifecycle directly via the Kubernetes API; we can promote to a CRD/operator if we end up with hundreds of distinct lifecycle states.
- **No on-chain agent identity registry.** ERC-8004 etc. are interesting but adopting them on day one couples us to a moving spec. We use platform-issued identities and can add on-chain attestation later.
- **No fine-tuning.** All model behavior is via prompting and tool use on frontier models. We do not fine-tune per-Darwin or per-strategy. (We may revisit for the planner if frontier models prove too expensive in production.)
- **No Temporal, pgvector, or Pulumi (substituted, not built).** Early drafts of this table name-dropped these; the as-built system covers each need another way, and adding them now would be redundant moving parts:
  - **Temporal** → the in-process LangGraph-style orchestrator loop + per-Darwin checkpoint store + hash-chained audit log already provide durable, resumable execution; platform billing / harvest / reproduction are idempotent maintenance sweeps, not complex sagas. (See BACKLOG "Temporal — Won't do".)
  - **pgvector** → per-Darwin embeddings live in an embeddable **LanceDB** store injected at the `episodic_memory` seam, so vectors never need a Postgres extension.
  - **Pulumi** → **Terraform + Helm** cover all infrastructure-as-code; a second IaC tool in real-language form would duplicate it.
  Each remains an easy add later if scale or team preference changes — but none is a missing capability today.
